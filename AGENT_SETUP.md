## Что нужно понять до подключения

Нужен агентный клиент: модель сама не читает диск, не запускает pytest и не открывает браузер. Клиент выполняет вызовы инструментов и возвращает результат модели. Доступ к модели в чат-интерфейсе агрегатора ещё не доказывает наличие API; проверь отдельно API endpoint, ключ, model ID, оплату/лимиты и поддержку tool calling.

У DeepSeek официальный API сейчас использует имя `deepseek-flash` для DeepSeek-V4.1-Flash-1017. У агрегатора имя и обслуживаемая версия могут отличаться: не подставляй официальный alias без проверки каталога и договора маршрутизации. Источник: [DeepSeek API](https://api-docs.deepseek.com/).

Встроенные подагенты Codex наследуют провайдера, права и MCP координатора. Файл роли может задавать модель, но не отдельного провайдера. Следовательно, нельзя просто указать DeepSeek в роли дочернего агента Sol, авторизованного через ChatGPT, и считать двухпровайдерную схему настроенной. Источник: [официальная документация OpenAI о подагентах](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## Рекомендуемая схема для двух подписок

```text
Пользователь → Codex CLI / приложение, Sol 6.1, вход ChatGPT
                  │ задания, чтение результатов, проверка
                  ├─ отдельный процесс исполнителя №1 → API агрегатора → DeepSeek
                  ├─ отдельный процесс исполнителя №2 → API агрегатора → DeepSeek
                  └─ локальные pytest / HTTP / Playwright / Docker
```

Sol запускает другой агентный CLI через терминальный инструмент, передаёт карточку задания и получает результат из файла/вывода. Это внешние исполнители: они не появятся автоматически во встроенном списке подагентов, их процессы, таймауты и результаты отслеживает координатор. MCP для этого не обязателен.

Выбор клиента исполнителя зависит от протокола:

1. **Есть совместимый Responses API:** можно использовать отдельные процессы Codex с отдельным пользовательским профилем провайдера. Совместимость streaming и tool calling необходимо подтвердить пробным заданием. У самого DeepSeek есть [инструкция интеграции с Codex](https://api-docs.deepseek.com/quick_start/agent_integrations/codex/); агрегатор не обязан поддерживать тот же API.
2. **Есть только Chat Completions/tool calling:** используй клиент с поддержкой этого провайдера, например OpenCode. Он допускает дополнительные провайдеры и неинтерактивный `opencode run`; конфигурацию бери для установленной версии из [Providers](https://opencode.ai/docs/providers/) и [CLI](https://opencode.ai/docs/cli/). Не переноси такую конфигурацию в Codex с `wire_api = "responses"` без совместимого endpoint.
3. **Есть только веб-чат:** автономный API-исполнитель пока не настроить этой схемой. Нужен API-тариф/другой провайдер либо ручная передача узких задач. Не автоматизируй личный веб-чат вместо недостающего API.

Наличие подписки ChatGPT не устанавливает условия оплаты агрегатора и API. Не передавай ChatGPT auth-файлы агрегатору. Координатор продолжает использовать штатный вход ChatGPT; исполнитель получает только ключ своего провайдера через окружение. Для API-платежей проверь условия конкретного аккаунта, не считай их частью чат-подписки по умолчанию.

## Минимальная конфигурация отдельного Codex-исполнителя

Ниже **шаблон**, не готовое подключение. Он применим только после проверки Responses API у выбранного агрегатора. Сохрани локально в `~/.codex/review-worker.config.toml`, не в `source/` и не как активный проектный provider override:

```toml
model = "REPLACE_WITH_AGGREGATOR_MODEL_ID"
model_provider = "review_aggregator"

[model_providers.review_aggregator]
name = "Review worker aggregator"
base_url = "https://REPLACE_WITH_AGGREGATOR_RESPONSES_BASE_URL"
env_key = "REVIEW_WORKER_API_KEY"
wire_api = "responses"

[agents]
enabled = false
```

Ключ задай в окружении процесса через менеджер секретов или скрытый ввод; не вставляй в задание модели, аргументы CLI, отчёт или Git. Настройка профиля не меняет основной профиль Sol. Профили актуального Codex — отдельные `<name>.config.toml`; настройки провайдера в проектном `.codex/config.toml` ограничены. См. [Advanced Configuration](https://learn.chatgpt.com/docs/config-file/config-advanced).

После заполнения профиля, проверки лимита расходов и создания карточки `scratch/tasks/C02.txt` из COORDINATION.md пример одного запуска из корня ревью:

```bash
mkdir -p scratch/tasks scratch/results
timeout 15m codex exec --profile review-worker --sandbox workspace-write \
  --output-last-message scratch/results/C02.md - < scratch/tasks/C02.txt
```

`scratch/tasks/C02.txt` нужно заполнить **до** запуска; каталог сам не создаёт задания. Это один процесс, не автоматический пул. Sol может запускать два таких процесса с разными ID через свой терминальный инструмент и собирать их результаты. Код выхода `timeout`/CLI проверяется отдельно: файл итогового сообщения не доказывает успешный запуск теста. Не используй бездумно `--dangerously-bypass-approvals-and-sandbox` ради фоновой работы. Сетевые ограничения и невозможность нового approval в headless-режиме могут потребовать заранее настроенного изолированного окружения; ошибку надо вернуть координатору, а не обходить полномочия.

Для Sol можно начать штатный локальный сеанс командой `codex --model gpt-6.1-sol`, если модель доступна аккаунту. После настройки исполнителя передай стартовый запрос ниже. Не заменяй неизвестный model ID случайным названием и не считай текущую сессию уже подключённой к агрегатору.

## Инструменты для полноценной проверки

| Возможность | Минимальный инструмент | Как использовать |
|---|---|---|
| Код, diff и происхождение дефекта | Встроенный terminal, `rg`, `git` | Закреплённый SHA, сравнение с базой, чтение требований; отдельный filesystem MCP обычно избыточен |
| Backend, гонки и сбои интеграций | Python/pytest, HTTP-клиент, fake-клиенты, barriers/events | Тесты с желаемым контрактом вне source; фиктивные credentials не делают реальные Google Sheets рабочими |
| Сборка и окружение | Node/npm, Docker Compose | Зависимости и build в отдельном runtime; конфиги ревью вне source; не мутировать исходники сборочными артефактами |
| Клики, формы, DOM, сеть, console и снимки | Playwright MCP либо уже доступный браузерный инструмент клиента | Интерактивное исследование; для стабильного воспроизведения сохранить Playwright-тест |
| Визуальная оценка скриншотов | Модель/клиент с image input | Проверить поддержку vision именно у выбранного endpoint; текстовый DOM доступен и без зрения |
| PR, требования, комментарии | Доступный GitHub connector или `gh` | Read-only достаточно для исследования; публикация требует явного поручения |

Установить Playwright MCP в Codex можно командой, которую выполняет владелец настроек:

```bash
codex mcp add playwright -- npx -y @playwright/mcp@latest --isolated
codex mcp list
```

Это пример из текущей документации; для воспроизводимого окружения после пробного запуска закрепи выбранную версию вместо `latest`. Команда меняет пользовательскую конфигурацию — в текущей задаче она не выполнялась. MCP каждого отдельного клиента настраивается отдельно; подключение в Codex не подключает его автоматически к OpenCode. Источники: [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp).

`--isolated` разделяет браузерные профили параллельных клиентов. Он не разделяет backend/таблицу и не является сетевой песочницей. Работай с локальным тестовым сайтом, а не с личным авторизованным браузером. Сначала используй accessibility/DOM snapshot для действий, затем screenshot для проверки внешнего вида. Если screenshots не принимаются моделью исполнителя, визуальную оценку выполняет Sol, а исполнитель может проверять DOM/HTTP.

Для C05/C06/C08 браузерный сценарий должен фиксировать выбранные курс, группу, работу, время, запрос мутации, немедленный ответ чтения и список на экране. Положительный ответ сервера и HTTP 200 главной страницы не подтверждают работу очереди. Если Google/GitHub подменены, явно отдели проверку UI и бизнес-логики от непроверенной реальной интеграции.

## Что нужно координатору помимо инструментов

Дополнительный «MCP для умения руководить» не требуется. Ему нужны [COORDINATION.md](COORDINATION.md), доступ к требованиям, карточки задач, реальные результаты команд, управление процессами и возможность повторить проверки. MCP — способ подключить инструменты, а не механизм, который сам превращает дешёвую модель в надёжного ревьюера.

Стартовый запрос после настройки и пробного запуска:

```text
Проведи ревью PR #68 по AGENT_TASK.md и COORDINATION.md.
Ты — координатор Sol 6.1. Начни с baseline, требований и CANDIDATES.md.
Используй два отдельных процесса дешёвых исполнителей через проверенный
профиль review-worker; максимум три после успешной приёмки первого пакета.
Не подменяй их встроенными Sol-подагентами без сообщения об этом.
Начни с узких проверок C02 и C04; третий пакет — запуск/UI C01.
Общие отчёты веди сам, исходники source/ не меняй.
Дай каждому уникальные каталоги и изолированные данные; проверяй exit codes.
Перепроверь каждое доказательство и разумные возражения перед findings/.
При проблемах API/квоты останови платные задания и сообщи точную причину.
Расходы допускаются только в заранее согласованном лимите провайдера.
Ничего не публикуй и не меняй в чужих сервисах.
```

Первый запуск считается настроенным только после того, как исполнитель действительно прочитал файл, выполнил безвредную локальную команду и сохранил проверяемый результат, а координатор его получил и перепроверил. Сейчас этот этап не выполнен: требуются сведения об агрегаторе и локальная настройка credentials.
