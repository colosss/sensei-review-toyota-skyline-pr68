## План самостоятельной проверки

### 1. Зафиксировать требования и область изменений

Изучи исходное задание хакатона, уточнения организатора, описание PR, ADR и документацию. Найди первичные источники требований; сохраняй URL и точные основания ожидаемого поведения. Если требование недоступно, явно отметь пробел вместо выдумывания. Построй таблицу «требование — реализация — проверка — результат». Отдели новые дефекты PR от ошибок, уже присутствующих в базовом коммите. Файл `source/docs/rewiev.md` — только источник гипотез, а не доказательство.

### 2. Базовая проверка

- Создай независимое окружение зависимостей и запиши версии Python/Node/Docker и пакетов.
- Запусти backend-тесты целиком, frontend-тесты, lint и production build. Сохрани команды, exit codes и логи. Не меняй lock-файлы ради прохождения сборки.
- Проверь штатный Docker-запуск, порты, доступность API, загрузку frontend и соединение frontend с backend. При доступности браузера пройди пользовательские сценарии; при его отсутствии укажи ограничение.
- Ошибки окружения отделяй от дефектов решения. Не объявляй все падения тестов багами без разбора причины.

### 3. Функциональные сценарии

Проверь индивидуальные и командные лабораторные, регистрацию студента, идентификацию, выбор курса/группы/работы, вход в очередь, повторную запись, выход, сдвиг позиции, просмотр преподавателем, смену статусов и закрытие дня. Проверь связь с результатами CI, допустимые статусы и правила повторной записи после выхода/завершения. Ожидаемое поведение определяй по требованиям, не только по существующим тестам.

### 4. Расписание

Проверь manual/GUAP, сопоставление курса и группы, нечётные/чётные недели, коррекции отмены/переноса/добавления, allowed labs, часовые пояса, точные границы открытия/закрытия, смену даты, несколько занятий за день, отсутствие расписания, ошибки источника и обновление YAML. Управляй временем через fake clock/freezegun в тестах, не меняй системные часы.

### 5. Конкурентность и сохранность данных

Особенно внимательно проверь фактически поддерживаемый однопроцессный backend:

- Одновременную запись одного студента и разных студентов; порядок, уникальность, потерю записей.
- Одновременные register/withdraw/shift/set-status/snapshot и проверку условий под блокировкой.
- Общую очередь для разных групп, лабораторных и команд: корректность ключей lock/cache, отсутствие смешивания данных.
- Устаревший кэш, инвалидацию после мутаций, чтение во время записи и ошибки после частичного выполнения.
- Конкурентное обновление расписания/курсов и YAML: частичные файлы, потерянные изменения, атомарность read-modify-write.
- Перезапуск backend, смену дня, закрытие прошлых дней, историю, повторный запуск архивации, дублирование и потерю строк.
- Взаимодействие backend и Apps Script при закрытии дня: локальный Python-lock не защищает внешний скрипт. Межсистемные гонки моделируй явно, не утверждай факт без воспроизведения.

Проверки делай детерминированными через barriers/events и управляемые fake-клиенты. Не полагайся только на sleep или случайные многократные запросы. Указывай, где сценарий проверяет реальное приложение, а где только модель.

### 6. Сбои и безопасность

Проверь недоступность Google/GitHub, квоты, таймауты, частично успешные batch-записи, повтор запроса и восстановление после ошибки. Fake-клиенты должны воспроизводить реальный контракт библиотек; неподдерживаемые предположения об API не считай доказательством.

Проверь подписи cookie, границы полномочий студента/администратора, валидацию идентификаторов и входных данных, path traversal, утечки секретов и опасные операции. Проверяй на синтетических данных локально. Запрет менять авторизацию в проекте sensei-mcp не ограничивает поиск дефектов в чужом решении. Однако замечание должно относиться к области PR и требованиям; унаследованные особенности фиксируй отдельно.

Проверки зависимостей можно выполнить, но наличие advisory само по себе не доказывает эксплуатируемый дефект приложения: укажи применимость и путь воздействия.

## Как оформлять найденное

Для каждого подтверждённого дефекта подготовь:

1. Краткий заголовок и приоритет с обоснованием воздействия.
2. SHA, файл и точные строки проверяемой версии; по возможности permalink GitHub.
3. Требование или контракт, которому противоречит поведение.
4. Условия и исходные данные, не содержащие секретов/PII.
5. Минимальные шаги и точную команду воспроизведения из чистого checkout.
6. Ожидаемый и фактический результат.
7. Падающий assertion/вывод/HTTP-ответы/состояние хранилища, подтверждающие дефект.
8. Почему дефект относится к изменениям PR. Если унаследован — явно отметь и вынеси отдельно.
9. Ограничения доказательства и возможные обоснованные возражения автора.

Тест регрессии должен проверять желаемый контракт и падать на проверяемой версии по причине дефекта. Не выдавай тест, который успешно подтверждает наличие бага, за «падающий регрессионный тест»: различай эти два формата. Не исправляй код для получения зелёного теста.

## Выходные материалы в общем репозитории (вне source/)

- `REPORT.md`: проверенная версия, окружение, команды, результаты, подтверждённые дефекты по важности, непроверенные области и краткий итог. Не заявляй «ошибок нет», если проверка ограничена.
- `REQUIREMENTS.md`: матрица требований и источников.
- `findings/<идентификатор>.md`: готовые тексты подтверждённых замечаний для GitHub Review по `findings/TEMPLATE.md`, без гипотез и дублей.
- `repro/<идентификатор>/`: минимальные тесты/скрипты воспроизведения и инструкция запуска. Используй уникальные имена, чтобы не затенить модули приложения.
- `evidence/<идентификатор>/`: логи, результаты и при необходимости скриншоты, очищенные от секретов и персональных данных.
- `CANDIDATES.md`: локально подготовленный реестр неподтверждённых гипотез, проблем окружения и унаследованных ошибок с причиной исключения из review. При явном поручении пользователя переноси обсуждение и распределение работы в Issues общего репозитория.

Проверяй все основные области, но качество доказательств важнее числа замечаний. Не придумывай дефекты ради количества. По завершении сообщи, что запущено, что проверено, сколько дефектов подтверждено и какие внешние зависимости мешают завершить остальные проверки. Оставь только необходимые контейнеры и явно сообщи, какие работают. Публикацию GitHub Review оставь человеку, если нет отдельного явного поручения на отправку. В итоговом замечании должны быть минимальный тест либо шаги, ожидаемый и фактический результат и существенный вывод: авторы PR могут не иметь доступа к приватному рабочему репозиторию.
