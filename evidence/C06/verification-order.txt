## 2. Ответы на поставленные вопросы проверки

### 2.1 «Список намеренно весь день / все статусы?»

Факты источника:

- `source/main.py:3416-3448` — `GET .../groups/{group_id}/labs/{lab_id}/queue`,
  docstring: «List the active queue for a group and lab». Реализация читает
  весь лист дня (`read_queue_rows(worksheet)`, 3431) и возвращает все строки
  без фильтра по group/lab/status (3434-3445), `size = len(rows)`.
- `source/main.py:3451-3486` — отдельный админский endpoint
  `/admin/courses/{course_id}/queue/today` с комментарием «all labs, all groups».
  То есть «весь день целиком» уже существует как отдельная админская операция;
  student-facing lab-route, отдающий то же самое, — не «намеренно весь день»,
  а незавершённая фильтрация.
- `source/frontend/.../QueueSection.jsx:329-359` — рендерит ответ как есть,
  без клиентской фильтрации; `t("queue.listTitle")` (ru) = «Очередь вашей
  группы», т.е. UI обещает как минимум группу, а не весь лист дня.
- ADR-queue-storage.md:20-25 — дневная очередь хранит позицию, группу, ФИО, ЛР,
  № пары, статус; студент читает «свой статус и позицию», преподаватель —
  «весь список». Это поддерживает наличие статусов в листе, но не отменяет
  scope группы на студенческой странице.

Вывод: «весь день» — не документированное намерение student-route.
«Все статусы» — наоборот, ADR прямо описывает лист со статусами и filter view
по статусам как штатную teacher-модель. Поэтому:
**«нет фильтра по status» само по себе дефектом не подтверждаю**, а отсутствие
group/lab-фильтра — подтверждаю.

### 2.2 «UI показывает ли lab/group/статус?»

- Строка списка: chip позиции + `entryName(entry)`, где `entryName` = team/FIO
  (`QueueSection.jsx:60-66`), т.е. **lab и group не показываются**.
- Статус: `secondaryAction` chip `queue.statuses.*` — **показывается**
  (`QueueSection.jsx:336-346`).
- № пары строки: не показывается; над списком есть только подпись текущей
  активной сессии `status.session` (`QueueSection.jsx:304-307`), а не пары
  каждой строки. Поле `session_no` в ответе есть, UI его игнорирует.
- Личная позиция: «Вы в очереди: позиция {{position}} из {{total}}»
  (`translation.json`, `queue.position`) берётся из `status.position` /
  `status.queue_size` (`QueueSection.jsx:243-245`).

Следствия для оценки:
- Смешение ЛР/групп в списке пользователь не может распознать: две строки
  «Иванов Иван» выглядят одинаково, хотя это разные люди/лаборатории. Это
  усиливает причину 1.
- Строка «отозван» **визуально отличима** (chip статуса), поэтому дубль
  позиции с ушедшей строкой — прежде всего presentation/data-smell, а не
  доказанный нумерационный дефект (см. 3.4).

### 2.3 Наблюдение [2,1,1] — scope

Воспроизведено и подтверждено: страница ЛР1 возвращает три строки
`[Иванов(ЛР1,pos 2), Иванов(ЛР2,pos 1), Петрова(ЛР1,pos 1)]`.
Важно: в этом сценарии **все три строки имеют session_no=2** (clock по
умолчанию `guap-mon-2`). Значит `[2,1,1]` объясняется **только смешением
лабораторий в списке** (причина 1), а не нумерацией по парам (причина 2).
Дубли «1» здесь — позиции в разных lab-очередях; двух одинаковых ожидающих в
одной ЛР нет. Отдельно `test_observed_list_mixes_other_groups_too` показывает
и утечку чужой группы (B-G2) в страницу B-G1.

## 3. Оценка каждой заявленной причины

### 3.1 Причина 1 — GET .../queue игнорирует group_id/lab_id

**Подтверждаю (reproduced, высокое доверие).** Механизм: `main.py:3416-3448`
строит ответ из `read_queue_rows` без фильтров; тот же список отдаётся для
ЛР1 и ЛР2; чужaя группа тоже попадает. Контракт: docstring самого endpoint,
frontend-URL с group/lab (`api/index.js:45-46,88-92`), отдельный админский
«all labs, all groups» endpoint, `queue.listTitle` = «Очередь вашей группы».
Наблюдаемое: `[2,1,1]`, идентичный ответ для ЛР2, строка B-G2 на странице B-G1.

Возражения/уточнения для финального текста:
- UI-заголовок «Очередь вашей группы» даёт авторам основание спорить именно с
  lab-фильтром. Самый неоспоримый тезис — **утечка чужой группы** и
  невозможность отличить строки без lab/group в UI. Lab-фильтр опирается на
  docstring и путь запроса; формулировка «for a group and lab» есть в коде.
- Не утверждать, что список обязан показывать только waiting: статусы — часть
  дневного листа по ADR.

### 3.2 Причина 2 — позиция в register считается по паре, а чтение — по дню

**Подтверждаю как рассогласование scope, с оговоркой о модели.**
- `store.register` (`store.py:426-433`) и ответ register (`main.py:3316-3319`)
  считают `position`/`queue_size` по `list_waiting(..., session_no=активная пара)`.
- `queue_status` (`main.py:3101,3169,3212-3214`) и `queue_list` (`3431`) читают
  без session-фильтра; `queue_size` — весь день.
- Наблюдаемо: обе регистрации вернули `{"position":1,"queue_size":1}`, а статус
  второй — `in_queue=true, position=1, queue_size=2`; список — `[1,1]`.
- Это внутреннее противоречие в одном UI: сразу после записи «1 из 1», после
  перезагрузки «1 из 2». Дефект существует независимо от того, какой scope
  авторы выберут правильным.

Оговорка: ADR (строки 125-127) описывает filter views по парам, что допускает
модель per-pair. Но `store.register:414` явно запрещает дубль «even across
sessions» — это признак одной дневной очереди, а не набора очередей по парам.
Поэтому ожидание авторского теста (уникальные 1..n для group+lab+день) не
противоречит контракту, но финальную формулировку лучше строить на
рассогласовании register↔status/list и «1 из 1» vs «1 из 2», а не на
постулате «позиции обязаны быть уникальны» без модели. Возможный фикс авторов
(читать по паре) тоже устранит противоречие — это допустимая альтернатива,
и её стоит назвать в замечании.

### 3.3 Причина 3 — set-status не перенумеровывает (позиционный аргумент)

**Подтверждаю (высокое доверие, механическая ошибка).**
- `main.py:3529-3531`: `_queue_set_status(spreadsheet, today, group_id,
  body.identifier, lab_short_name, body.status, group_ids)`.
- `store.set_status(..., status, session_no=None, group_ids=())`
  (`store.py:507-515`): седьмой позиционный аргумент `group_ids` попадает в
  `session_no`; `_renumber_waiting` (`store.py:543,384-397`) фильтрует
  `row.session_no == [group ids]` — сравнение int со списком, не совпадает
  ничего, обновлений нет.
- Наблюдаемо: после «сдал» первого из двух ожидающий остаётся на позиции 2,
  а статус отвечает «position 2 of 1». Это самопротиворечие одного ответа
  (позиция в очереди размера 1 не может быть 2) плюс видимое «2 из 1».
- Контракт: `store.set_status` сам вызывает `_renumber_waiting` (намерение
  авторов), UI печатает «позиция N из M» из тех же полей. Здесь нет спора о
  модели очереди: даже без перенумерации ответ не должен репортить 2 из 1.

Проверил остальные вызовы store на ту же ошибку: `withdraw` (`main.py:3357`)
передаёт `session_no=None` — корректно; `shift` (`3403-3405`) и `register`
(`3309-3311`) — корректно. Ошибка только в set-status.

### 3.4 Причина 4 — «ушедшая строка сохраняет позицию, в списке дубли»

**НЕ подтверждаю как отдельную причину-дефект.** Наблюдение воспроизведено
(`[отозван 1, ждёт 1, ждёт 2]`, после возврата тот же человек в двух строках),
но заявленный инвариант «все показанные позиции уникальны» не выведен из
контракта:

- ADR прямо описывает дневной лист со статусами и filter views по статусам;
  список (и раньше — весь лист) штатно содержит не-waiting строки.
- UI показывает chip статуса, т.е. «отозван» отличим от «ждёт».
- Позиции **ожидающих** строк после выхода остаются уникальными 1..2
  (`withdraw` вызывает `_renumber_waiting` без session-фильтра; в сценарии
  получается ждёт 1 и ждёт 2). Дубль — между неактивной и активной строками.
- «Тот же человек дважды» после выхода+возврата — следствие хранения истории
  дня, а не нарушения нумерации; отдельного требования скрывать ушедшую
  строку нет.

Рекомендация Sol: не выделять это в отдельный дефект без контракта. Либо
оставить observation/UX-замечание (слабое, баллов не даст), либо, если
хочется зафиксировать, переформулировать как «list отдаёт неактивные строки
со stale position в ответе, где `size` включает их, а `queue_size` статуса —
нет» — но это уже другой, более слабый тезис и требует решения product-scope.
Скриншот для этого не нужен: `[2,1,1]` полностью объясняется причиной 1.

## 4. Session ambiguity — отдельно

- `session_no` строки берётся из активного слота: `session_no_from_slot(
  session.slot_id)` (`main.py:3277`, `schedule_window.py:212-215`), последняя
  цифра id (`guap-mon-1` → 1, `guap-mon-2` → 2); fake clock переключает именно
  `slot_id`, что соответствует реальному seam.
- В UI пара каждой строки не отображается, а подпись «Ближайшая защита»
  описывает только текущую активную сессию. Поэтому строка, записанная в пару 1,
  в пару 2 выглядит как строка текущей очереди с позицией 1 — это усиливает
  impact причины 2, но самостоятельной причиной я её не считаю.
- В сценарии скриншота `session_no` всех строк = 2; смешение пар к `[2,1,1]`
  отношения не имеет (см. 2.3).

## 5. Проверка admin positional bug — итог

Подтверждён на уровне источника и HTTP: единственный неверный позиционный
вызов — `_queue_set_status(..., body.status, group_ids)`; `group_ids` уходит в
`session_no`, `_renumber_waiting` не находит строк, ответ статуса показывает
«position 2 of 1». `withdraw`, `shift`, `register` позиционно корректны.
Тест `test_regression_set_status_renumbers_the_remaining_waiting_queue` падает
именно на ожидании 1..n и на `position <= queue_size` — обе части обоснованы
поведением самого store (вызов `_renumber_waiting`) и семантикой полей статуса.

## 6. Не-C06 наблюдения (подтверждаю как observation, не как дефект C06)

- **Идентичность = ФИО.** Два разных студента с одинаковым ФИО и разными GitHub
  в фикстуре: второй видит статус первого (`in_queue=true, position=1`) и
  получает 409 `ALREADY_IN_QUEUE`. Воспроизведено. Контракт на разрешение
  однофамильцев не заявлен, тест правильно не содержит regression-assert.
  Отдать в C02/C04; зелёные store-тесты C02 с одной идентичностью этот случай
  не покрывают.
- **C05:** `_get_queue_cache` импортирован, но не вызывается; status/list читают
  лист напрямую, запись видна сразу. Это не доказывает отсутствие C05-эффекта
  на реальном Sheets/браузере.
- **C08:** shift 1000 в ЛР1 вернул old=1/new=2 (ограничение концом очереди) —
  арифметического дефекта нет; «странность» скриншота объясняется причиной 1.

  «ждёт» — это следует из кода (нет закрытия пары), но отдельного требования
  на этот flow нет.
- Независимость подтверждена только для набора тестов C06; другие пакеты не
  проверялись. Ничего не публиковал и не менял, кроме этого файла.
