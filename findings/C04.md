## Результат и первопричина

Публичный `/register` проверяет лишь существование аккаунта через `GET /users/{login}` (`main.py:1000-1006`). Даже если GitHub B уже привязан к строке B, повторение тех же ФИО и логина отвечает `already_registered` и ставит `student_session`. Подпись подтверждает серверную выдачу, но не владение личностью. Очередь принимает эту cookie через `_require_student_session`; известные публичные сведения становятся полномочиями над чужой строкой.

Ожидается: неподтверждённый посетитель не получает полномочий B; его мутация отклоняется, статус B остаётся `ждёт`, позиция неизменна. Факт: посетитель получает cookie B, withdraw возвращает 200 и меняет статус на `отозван`; на отдельном свежем fixture shift возвращает 200 и сдвигает B с 1 на 2, за C. Withdraw/shift — два проявления одной причины, не две находки.

## Отнесение к PR и ограничения

Сравнение с базой `eef98bb373c71e9e4e7df4258e1fe5b4b4c5ac39` статическое: публичная форма унаследована, но в базе нет `student_session`, `build_student_session`, queue routes и пакета `grading/queue`. PR добавляет выдачу подписанной cookie и мутации, доверяющие ей. Находка не о самом публичном вводе ФИО или записи GitHub в пустую ячейку — это было раньше. На базе поведение не запускалось.

Fake GitHub соответствует использованному контракту status_code; fake Sheets моделирует достигнутые чтения/записи, не реальные квоты/ошибки. Patch CI влияет только на успешный setup регистрации в очереди; withdraw/shift не проверяют GitHub владение и после прохождения setup. Внешние Google/GitHub/OAuth и браузер не проверялись. Только индивидуальные ЛР, без гонок. Требование знать точное ФИО/логин ограничивает атаку: ФИО доступно в публичном queue list, путь узнавания GitHub login через данный UI не исследован. Rate limiting замедляет, но не доказывает личность. OAuth `queue_session` присутствует в PR, но не требуется для этих мутаций; исправление не обязано использовать именно его, достаточно реальной проверки личности.

Сильнейшее возражение: «форма сознательно упрощена и унаследована, это не OAuth-контракт». Да, форма унаследована и комментарий 1015-1016 явно выбирает её вместо отдельного OAuth; поэтому мы не заявляем нарушение обязательного OAuth-метода. Дефект — новое полномочие изменять чужую очередь после знания публичных данных. Реальные изменения B доказаны отдельными запросами и состоянием хранения; подпись cookie сама по себе этот риск не устраняет.

## Текст для исходного GitHub Review

**[P1] Не выдавайте полномочную сессию очереди по одному знанию ФИО и GitHub login**

В `main.py:1040-1055` повторная публичная регистрация уже привязанного студента возвращает `already_registered` и выдаёт `student_session` без проверки владения GitHub-аккаунтом. `GET /users/{login}` выше проверяет лишь существование логина. При этом `/queue/withdraw` и `/queue/shift` считают предъявителя этой cookie авторизованным студентом (`_require_student_session`, строки 2940-2945, вызовы 3332/3380).

Минимальные шаги на SHA `20bea22cf4a1cbc19634a984883ff52764ce9d6d` в синтетическом изолированном курсе:

1. Курс `review-c04`, группа `C04-G`, индивидуальная ЛР `1` с short-name `ЛР1`; в ростере уже есть `Студент Бета` с GitHub `c04-student-b`. Занятие открыто, CI допустим. B записан в очередь, статус `ждёт`; для проверки сдвига C стоит за ним.
2. В НОВОЙ сессии, без cookie и без GitHub OAuth, выполнить:
   `POST /courses/review-c04/groups/C04-G/register`
   с JSON `{"surname":"Студент","name":"Бета","patronymic":"","github":"c04-student-b"}`.
   Ответ: HTTP 200, `status=already_registered`, сервер выставляет cookie.
3. Этой же сессией выполнить `POST /courses/review-c04/groups/C04-G/labs/1/queue/withdraw` без тела. Фактически HTTP 200, B меняется `ждёт -> отозван`.
4. На свежем исходном состоянии вместо шага 3 выполнить `POST /courses/review-c04/groups/C04-G/labs/1/queue/shift` с `{"delta":1}`. Фактически HTTP 200, B с позиции 1 попадает на 2, за C.

Ожидается, что неподтверждённая личность не получает сессию B и не меняет его запись; мутация должна быть отклонена, состояние B неизменно. Контроль без cookie возвращает 401, а с собственной сессией A — 404 без изменения B. Значит обход достигается именно выдачей чужой личности, а не отсутствием проверки cookie в мутации.

Изолированный regression на реальных FastAPI endpoint/store функциях (fake Sheets и только existence-check GitHub, без реальной сети) трижды дал `2 failed, 1 passed`, exit 1. Существенные assertions: `withdraw HTTP 200, entry status 'отозван'` и `shift HTTP 200, position 1 -> 2`. Доступ к приватному репозиторию ревью для ручных шагов выше не нужен.

Это новое воздействие PR: публичная форма существовала в базе `eef98bb…`, но не выдавала cookie полномочий и очереди там не было (статическое сравнение, без исполнения базы). Требуются точные ФИО и публичный login; захват GitHub-аккаунта не заявляется. Одна причина затрагивает обе операции. Полная реальная интеграция и браузер этим тестом не проверены.
