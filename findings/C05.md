## Текст для исходного review / самодостаточные шаги

**Согласуйте конкурирующие reload с успешной мутацией.** Кнопка Refresh не блокирует Join и не помечает чтение устаревшим. Оба reload безусловно записывают status/list по завершении Promise.all. Если чтение, начатое до join, завершилось после post-join reload, оно возвращает экран в состояние до записи, сохранив success notice.

На этом SHA, в открытом занятии с допустимым CI:
1. На странице ЛР заполнить форму студента, ещё не стоящего в очереди. В примере в очереди только Петрова, Иванов не записан.
2. Нажать «Обновить». Через devtools/управляемый proxy задержать доставку его list GET `/queue`, уже прочитанного сервером до записи. Не менять body. Ответ status этого чтения также относится к состоянию до записи.
3. Пока Refresh ожидает ответ, нажать «Записаться». Дать POST и вызванным им новым GET завершиться: видны «Вы записаны в очередь», позиция 2 из 2, Петрова и Иванов, кнопка выхода.
4. Доставить ранее удержанный list GET неизменным. Факт: success notice остаётся, Иванов и собственная позиция исчезают, снова предложена кнопка «Записаться». В хранилище Иванов всё ещё `ждёт` на позиции 2.
5. Одно новое «Обновить» возвращает строку, позицию и кнопки управления.

Ожидается: ранее начатое чтение не стирает состояние, уже полученное после подтверждённой мутации. Это не требование нулевой задержки Google Sheets: новое состояние уже было успешно прочитано и отрисовано. Воздействие P2 — ложное отсутствие записи, недоступные до обновления выход/сдвиг, повторные попытки записи. Потеря данных в хранилище не заявляется.

## Проверенный сценарий

`repro/C05/browser_stale_reload.js` — готовый Playwright function snippet для `browser_run_code_unsafe(filename)`. Стенд: настоящий построенный pinned frontend и реальные API/store/auth, отдельные synthetic Sheets/GitHub/CI/window. Запуск по `repro/C01/README.md`, API18280/UI18281, API base изменяется только в served bytes. Script сначала сбрасывает только fixture и cookies, удерживает один настоящий ответ, затем проверяет DOM/storage и восстановление. Это observation scenario, НЕ passing regression желаемого поведения, receipt pytest не требуется.

## Отнесение и ограничения

QueueSection.jsx добавлен целиком в PR (+368), базой этого пути нет. Сравнение статическое, база не запускалась. Старые ответы в reload не имеют generation/abort guard. Это отличается от C06: здесь содержимое списка устаревает по времени, а не смешивается по group/lab.

Сильнейшее возражение: задержка управлялась искусственно. Да, это детерминированное моделирование допустимого завершения двух сетевых запросов в обратном порядке; данные ответов не подделаны. Заявляется узкий race «Refresh одновременно с Join», не установленная исходная причина жалобы коллеги, cache TTL или измеренная production latency. Реальная Google/GitHub интеграция не проверена. Исправление не привязано к конкретной реализации, но старое чтение не должно выигрывать у нового после мутации.
