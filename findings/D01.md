## Замечание / воспроизводимый сценарий

**Не удаляйте лист на основании устаревшего снимка без заявленной защиты от изменений.** `snapshot_sheet` читает строки один раз, затем строит appendCells и deleteSheet в одном batch. Атомарность этого batch защищает две записи друг относительно друга, но не чтение, предшествовавшее внешней правке.

Собственный документ PR `docs/SETUP.md:97-105` адресует обеим сторонам backend/Apps Script проверку полноты и шаг «удалить лист очереди, только если он не менялся с момента чтения». На129-130 прямо описан случай правки листа прошлого дня при копировании: лист должен остаться для повторного прогона. Преподаватель правит таблицу напрямую по ADR-queue-storage.md:110-113.

Минимальное воспроизведение, управляемый fake Sheets (или две скоординированные стороны в отдельной разрешённой тестовой таблице):
1. В листе `Очередь-2026-11-07` есть строка Иванова, в истории её ещё нет. Дата backend2026-11-08, запускается snapshot_sheet этого листа.
2. После получения backend снимка листа, но ДО применения batch, внешний писатель добавляет строку `Новиков Олег` той же ЛР. Это успешная внешняя запись; backend о ней не узнаёт. Для детерминизма fake-транспорт вставляет правку на входе batch_update, перед любым применением его requests; fail_mode не используется.
3. Backend атомарно добавляет в историю только исходный снимок и удаляет весь лист.

Ожидается: новая строка либо в архиве, либо исходный лист сохранён для повторной обработки. Факт: история содержит только прочитанные ранее строки, Новикова нет, лист удалён. Второе проявление той же причины: поздняя отметка Иванова `сдал` заархивирована как прежнее `не_дошло`, источник удалён.

P2: требуется узкое окно внешней правки прошлого дня, но результат — необратимая потеря строки/результата в обычном доступном приложению архиве. Не утверждается постоянная потеря у провайдера с его version history и не объявляется сбой обычной однопроцессной дневной записи.

## Важные ограничения доказательства

- Только contract-shaped fake Sheets; реальные Sheets/Apps Script и production timing не проверялись. Это детерминированный сценарий внешней записи между чтением и применением batch, не частичный batch и не межпроцессная ошибка.
- Старый полный тест-пакет содержит control `before_delete`, имитирующий append-success/delete-failure ВНУТРИ одного атомарного batch. Такой контроль НЕ соответствует реальному API и НЕ используется как доказательство. Sol отдельно запускал только две корректные regressions. Старые хэшированные inputs/receipts не переписаны; оговорка в `evidence/D01/contract-caveats.txt`.
- Повторное чтение перед batch само по себе НЕ CAS: после него тоже остаётся окно. Нельзя обещать, что один re-read полностью устраняет потерю; замечание требует согласовать заявленный контракт защиты с архитектурой внешних писателей и сохранением исходных данных. Code.gs имеет best-effort re-read guard, но он не доказывает абсолютную гарантию.
- Возражение «ночью студент не записывается» ограничивает impact, но не исключает ручную правку преподавателя; SETUP отдельно описывает этот случай, а lazy snapshot запускается первым запросом нового дня. Без внешнего писателя этот сценарий не возникает.
