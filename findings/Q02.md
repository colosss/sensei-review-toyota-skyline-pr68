## Замечание / минимальные шаги

**Передайте group_ids в правильный параметр store.set_status.** Сейчас `_queue_set_status(spreadsheet,today,group,fio,lab,status,group_ids)` помещает список групп в `session_no`. Затем `_renumber_waiting(...,session_no)` фильтрует `row.session_no == список`, ничего не находит и тихо оставляет старые позиции.

В одном открытом занятии, одной группе и ЛР:
1. A и B записываются в очередь, позиции1 и2. У обоих допустимый CI.
2. Администратор с действующей admin-session вызывает `POST /admin/courses/review-c06/groups/B-G1/labs/1/queue/set-status` с `{"identifier":"Иванов Иван","status":"сдал"}` для A.
3. Факт:200 updated, A действительно `сдал`, B остаётся `ждёт` с position2. `/queue/status` B возвращает position2, queue_size1: «позиция2 из1».

Ожидается, что оставшаяся ожидающая очередь перенумерована1..n, B имеет position1 при size1. Основание — store.set_status явно вызывает renumber, статус и UI определяют position относительно queue_size, а не неизменный номер талона. Воздействие P2: штатная операция преподавателя оставляет некорректные личные позиции/порядок.

## Отнесение / возражение

Queue API/store новые в PR, статическое сравнение с базой проверено; база не запускалась. Это независимо от C06/Q01: одна группа/ЛР и одна пара, только неверная передача аргумента.

Возражение «абсолютные номера должны сохраняться» не соответствует явному renumber в реализации и собственному знаменателю size1. Read-only admin UI сознательный (C07), но опубликованный backend set-status обязан выполнять свой контракт; отсутствие кнопки не делает API-код недостижимым. Реальные Sheets, browser admin и несколько процессов не проверялись. Возможный фикс с именованным аргументом — иллюстрация причины, приложение в ревью не исправлялось.
