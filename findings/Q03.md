## Текст для review / самодостаточное воспроизведение

**Сохраните стабильную личность при переходе от ростера к очереди.** Ростер различает участников по GitHub username, но очередь хранит и ищет только `(group,lab,fio)`. Двое реальных тёзок с разными handles схлопываются в одну мутабельную запись. Это происходит даже если каждый вошёл строго под собственным логином.

В одной группе разместить в ростере:
- A: `Иванов Иван`, GitHub `c06-ivanov-a`;
- B: `Иванов Иван`, GitHub `c06-ivanov-b`;
- Петрова: `Петрова Анна`, GitHub `c06-petrova`.

Каждому выдать собственную корректную student-session. В изолированном тесте это `build_student_session` с app signer и СВОИМ username, без публичного register, без присвоения логина A. Это предпосылка надёжной идентификации, не проверка реального OAuth callback.

1. A: `POST /courses/review-c06/groups/B-G1/labs/1/queue/register` →200, position1.
2. B, который в очередь не записывался: `POST .../queue/withdraw` → фактически200, строка A меняется на `отозван`, status A больше не in_queue.
3. На свежем состоянии A и Петрова записаны1/2. B: `POST .../queue/shift` с `{"delta":1}` →200, A перемещается с1 на2 за Петрову.
4. Контроль: Петрова под собственным отличным ФИО отзывает только свою строку, A остаётся неизменён.

Ожидается отказ B (точный код несущественен) и неизменная запись A либо операция над собственной записью B, если она существует. P2 из-за предусловия одинаковых ФИО в одной группе; воздействие — целостность чужой очереди, не захват GitHub. Дополнительно B не может независимо записаться в ту же ЛР: FIO duplicate check считает его уже ожидающим.

## Требование, база, ограничения

Полного внешнего ТЗ о тёзках нет. Основание — собственный контракт authenticated-student операций: `sheets_context` однозначно находит разные строки по разным usernames и теряет это различие только при FIO-key в очереди. Условия exact-FIO duplicate в ростере возможны; уникальность ФИО конфигом не проверяется. При policy «все ФИО уникальны» воздействие исчезает, но такая предпосылка не установлена.

Это НЕ дубль C04: там непроверенные публичные данные дают чужую личность; здесь даже безупречно удостоверенный B имеет свой login, но ошибочный ключ хранения даёт ему A. Исправление аутентификации C04 не устраняет FIO collision. Queue schema и маршруты добавлены PR, сравнение базы статическое, база не запускалась.

Fake Sheets, synthetic CI/window; real Google/GitHub/browser и частота коллизий в production не проверены. Не утверждается, что реальный OAuth создаёт student_session: тест изолирует поведение downstream после корректной удостоверенной сессии. Приложение не исправлялось.
